# Apokolips OS — BIOS Bootloader Specification

**Status:** Active implementation specification — BL-1, BL-2, and BL-3 hosted/QEMU milestones implemented; Oracle VirtualBox validation pending  
**Document version:** 0.2  
**Target architecture:** x86_64 / AMD64  
**Initial firmware:** Legacy BIOS-compatible VirtualBox firmware  
**Boot medium:** Disposable raw virtual-disk image  
**Related documents:** `plan.txt`, `ARCHITECTURE.md`

---

## 1. Purpose

This document specifies the first boot path for Apokolips OS. It defines the disk-image layout, boot stages, initial CPU environment, loader responsibilities, error behaviour, and the contract that will eventually transfer control to the Apokolips kernel.

The first implementation milestone is intentionally small: BIOS loads an original Apokolips OS boot sector, that sector loads our second stage, and the second stage displays a clear status message. Kernel loading and the transition to 64-bit mode are later milestones. They must not be treated as already implemented.

The bootloader will be written specifically for Apokolips OS. It will not use another operating system's bootloader or copy code from another OS project.

## 2. Scope and explicit limitations

### 2.1 Included in the initial BIOS path

- A 512-byte BIOS boot sector.
- A small second-stage loader stored at a fixed, documented disk location.
- BIOS Enhanced Disk Drive (EDD) reads using INT 13h extensions.
- Preservation of the BIOS boot-drive number.
- Basic text diagnostics and controlled halt on failure.
- A reproducible image layout generated by project build tools.

### 2.2 Deferred until later bootloader milestones

- Reading arbitrary filesystems or partition tables.
- General-purpose filesystem support.
- UEFI and Secure Boot.
- CHS disk-read fallback.
- Multiple boot menu entries and interactive configuration.
- Network boot.
- Cryptographic signature verification.
- Loading arbitrary third-party executable formats.
- Physical-machine compatibility claims.

The initial image is a raw, unpartitioned boot image intended for a controlled VirtualBox test. It is not an installer and must never be written to the host laptop's physical disk.

## 3. Terminology

- **LBA:** Logical Block Address, numbered from sector zero.
- **Stage 1:** The 16-bit BIOS boot sector loaded by firmware.
- **Stage 2:** The Apokolips second-stage loader loaded by Stage 1.
- **EDD:** BIOS Enhanced Disk Drive services, accessed through INT 13h extensions.
- **Boot drive:** The BIOS device number supplied in register DL.
- **Boot manifest:** A fixed-format metadata record describing the kernel payload.
- **Kernel hand-off:** The documented transfer of CPU control and boot information to the kernel entry point.

## 4. Initial disk-image layout

### 4.1 Sector assumptions

The first implementation targets a VirtualBox BIOS boot image with 512-byte logical sectors. This is an initial test constraint, not a universal storage-device assumption.

The image is a raw disk image with no partition table. Sector zero is the BIOS boot sector. The first version does not attempt to parse MBR partitions or filesystems.

### 4.2 Reserved layout

| LBA range | Size | Purpose |
|---|---:|---|
| 0 | 1 sector | Stage 1 boot sector |
| 1–32 | 32 sectors | Reserved Stage 2 area (16 KiB maximum in initial layout) |
| 33 | 1 sector | Boot manifest |
| 34 onward | Variable | Kernel payload in later milestones |
| Remaining sectors | Variable | Reserved for future image layout |

All offsets are expressed in 512-byte sectors for this initial target. The image builder must reject an oversized Stage 2 binary rather than truncate it.

### 4.3 Image-builder responsibilities

The image builder is a host-side development tool, not part of the bootloader. It must:
1. Create or validate the raw image size.
2. Place the 512-byte Stage 1 binary at LBA 0.
3. Pad and place Stage 2 in the reserved LBA 1–32 area.
4. Write the manifest at LBA 33 when the manifest format is implemented.
5. Place the kernel payload at the LBA declared in the manifest.
6. Check all component sizes and sector boundaries.
7. Verify the boot signature and expected image offsets.
8. Produce a report containing component sizes, LBAs, checksums, and image size.

The first status-message milestone may use a fixed test image with the manifest and kernel area left unused. The image builder must still enforce the Stage 1 and Stage 2 layout.

## 5. Stage 1 — BIOS boot sector

### 5.1 Firmware entry conditions

For the initial target, Stage 1 may rely only on the following BIOS boot conditions:
- Firmware has loaded the first 512-byte sector to physical address `0x7C00` (some firmware may represent this as an equivalent segment:offset pair).
- Firmware has transferred control to the boot sector.
- Register DL contains the BIOS boot-drive number.
- The final two bytes of the sector are the boot signature `0x55, 0xAA`.

No other general-purpose register, segment value, stack, interrupt state, or memory content may be assumed to be initialized in a useful way.

### 5.2 First-stage responsibilities

Stage 1 must perform only the work needed to load and enter Stage 2:

1. Establish a known real-mode segment and stack environment without overwriting the boot sector or Stage 2 load area.
2. Save the incoming boot-drive value from DL before using BIOS calls.
3. Check whether BIOS EDD extensions are available using the documented INT 13h extension check.
4. Read the fixed Stage 2 sector range (LBA 1–32) into the agreed load address using an EDD Disk Address Packet (DAP).
5. Check the BIOS carry flag and returned status after disk operations.
6. Restore the saved boot-drive value in DL and transfer control to the Stage 2 entry point.
7. On failure, print a short diagnostic using BIOS teletype output where available, then halt safely.

### 5.3 Stage 1 constraints

- The complete boot sector, including its final signature, must be exactly 512 bytes.
- The boot signature must occupy offsets 510 and 511.
- The Stage 1 implementation must fit within the available boot-sector space; no partition table is present in this initial raw-image format.
- Stage 2 is loaded to the fixed physical address `0x8000` in the initial design.
- Stage 2 occupies no more than 32 sectors (16 KiB) in this initial layout.
- The Stage 2 load range must not overlap Stage 1, the active stack, or BIOS data areas.
- The DAP and all data passed to BIOS services must be correctly aligned and formatted as required by the BIOS interface.
- Stage 1 must not assume that one BIOS disk read can cross arbitrary 64 KiB boundaries. The fixed initial Stage 2 range is deliberately small and must be laid out to avoid such a boundary crossing.
- No kernel loading, memory-map parsing, protected-mode transition, or long-mode transition is required in the first Stage 1 milestone.

### 5.4 EDD-only initial policy

The first implementation will require EDD support. If the BIOS does not report EDD support, Stage 1 will display a clear error and halt. CHS fallback may be designed later if a tested compatibility requirement justifies its extra complexity.

This policy keeps the first loader smaller and makes its disk-addressing assumptions explicit.

### 5.5 Stage 1 failure cases

At minimum, distinguish these conditions in diagnostics:
- EDD extensions unavailable.
- Stage 2 disk read failed.
- Stage 2 transfer target or image layout invalid, when detectable.

The boot sector must not jump into Stage 2 after a failed or incomplete read.

## 6. Stage 2 — second-stage loader

### 6.1 Initial responsibilities

The first Stage 2 implementation will:
1. Establish its own known real-mode execution environment.
2. Preserve the BIOS boot-drive number passed by Stage 1.
3. Display an unmistakable message such as `APOKOLIPS OS: STAGE 2 LOADED`.
4. Display a diagnostic if its expected entry conditions are not met, where detectable.
5. Halt in a controlled loop.

The first Stage 2 milestone does not load a kernel. Reaching the message proves only that Stage 1 successfully transferred control to Stage 2.

### 6.2 Later responsibilities

After the Stage 1-to-Stage 2 transfer is reliable, Stage 2 may be extended to:
- Read and validate the boot manifest.
- Load the kernel payload in bounded disk-read chunks.
- Validate the kernel image format and architecture.
- Collect the BIOS memory map using E820 where supported.
- Enable and verify the A20 address line.
- Establish the GDT and required CPU state.
- Build initial page tables.
- Enter x86_64 long mode.
- Construct the versioned boot-information structure.
- Transfer control to the kernel entry point.

Each capability must be implemented and tested as a separate milestone.

## 7. Boot manifest format — planned

The manifest is reserved at LBA 33 in the initial image layout. Its binary format must be specified and versioned before kernel loading is implemented.

The first proposed manifest contains:
- Fixed magic bytes identifying an Apokolips boot manifest.
- Manifest format version.
- Header size and total manifest size.
- Target architecture identifier (x86_64).
- Kernel image format identifier.
- Kernel payload starting LBA.
- Kernel payload byte length.
- Kernel payload sector count.
- Kernel payload checksum algorithm identifier and checksum value.
- Required boot protocol version.
- Reserved fields that must be zero in version 1.

### 7.1 Validation requirements

Stage 2 must reject a manifest if:
- The magic or version is unsupported.
- Header or total sizes are invalid.
- Architecture or image format is unsupported.
- The payload length is zero or exceeds the configured maximum.
- LBA arithmetic overflows or points outside the image bounds known to the loader.
- The checksum does not match.
- Reserved fields violate the version's rules.

The exact field offsets, widths, byte order, checksum algorithm, and maximum kernel size are **not yet frozen**. They must be recorded in a separate binary-format specification or a precise section of this document before code relies on them.

## 8. Kernel image loading — planned

The architecture document anticipates an ELF kernel image. The bootloader must not assume that an ELF file can be copied to one arbitrary address and executed.

Before implementing ELF loading, the project must specify:
- Supported ELF class, endianness, machine, type, and version.
- Which program-header types are accepted.
- Maximum number of program headers.
- Maximum image size and segment count.
- Required alignment rules.
- Accepted physical load-address range.
- Virtual-address mapping policy.
- Entry-point validation.
- Handling of zero-filled segment tails (for example, `p_memsz` greater than `p_filesz`).
- Rejection of overlapping, malformed, or out-of-range segments.

The first kernel-loading implementation should support only the narrow ELF subset produced by the project's own linker script. General ELF compatibility is not a goal.

All segment arithmetic must be overflow-checked. The loader must validate every destination range before writing to it. The initial kernel image should be constrained to physical addresses representable by the loader's selected loading mode.

## 9. Memory map collection — planned

The later Stage 2 loader will request the BIOS E820 memory map and retain each returned entry. It must:
- Verify the BIOS response signature and returned entry size.
- Handle continuation tokens correctly.
- Bound the number of entries and total memory-map storage.
- Preserve memory types and attributes.
- Reject or report malformed responses.
- Mark loader-owned buffers and the kernel image as reserved in the final hand-off map, or provide enough ownership metadata for the kernel to reserve them.
- Avoid treating unknown or reserved memory types as usable RAM.

The kernel must independently validate the supplied map before using it.

## 10. A20, GDT, paging, and long-mode transition — planned

The transition to 64-bit mode is a later milestone and requires its own tests.

The loader must:
1. Enable A20 using a method appropriate to the supported BIOS/VM environment and verify the result.
2. Check CPU support for long mode and required paging features using CPUID.
3. Construct a valid GDT with documented selectors.
4. Build page tables that satisfy x86_64 long-mode requirements.
5. Enable protected mode and paging in the architecturally required order.
6. Enable long mode through the documented EFER mechanism.
7. Perform the far control transfer into 64-bit code.
8. Establish a known 64-bit stack and clear or define the required register state.
9. Keep interrupts disabled until the kernel installs valid interrupt handling.
10. Jump to the validated kernel entry point.

The initial page-table mapping strategy must be documented before implementation. A minimal identity map is sufficient for an early bring-up kernel if it covers the executing loader code, stack, page tables, and kernel entry. Higher-half mappings can be added when the kernel linker layout is finalized.

If the CPU does not support the required mode or setup fails, the loader must report the failure and halt rather than attempting an invalid transition.

## 11. Kernel hand-off contract — planned

The bootloader and kernel must share a versioned ABI. The exact register assignments and structure layout must be frozen before the first kernel hand-off test.

The hand-off contract must define:
- Kernel entry address and execution mode.
- Calling convention and required stack alignment.
- Boot-information pointer location.
- Boot-information magic and version.
- Memory-map pointer, entry count, entry size, and format.
- Kernel image physical and virtual ranges.
- Framebuffer metadata, if supplied.
- Boot drive and boot-medium metadata, if supplied.
- Reserved memory ranges and ownership.
- Interrupt state on entry.
- Which CPU features and page-table mappings are guaranteed.
- Which registers are defined and which are unspecified.

The kernel must validate the boot-information block and every referenced range before use. A protocol version mismatch or invalid pointer must result in a controlled early-kernel failure.

## 12. Error handling and diagnostics

The loader must fail closed. It must never transfer control after a known failed disk read, invalid image, unsupported CPU mode, or malformed kernel image.

Diagnostics should be short, consistent, and useful during early boot. Suggested messages include:
- `APOKOLIPS: BIOS BOOT`
- `APOKOLIPS: STAGE 2 LOADED`
- `ERROR: EDD NOT AVAILABLE`
- `ERROR: STAGE 2 READ FAILED`
- `ERROR: INVALID BOOT MANIFEST`
- `ERROR: KERNEL IMAGE INVALID`
- `ERROR: CPU MODE UNSUPPORTED`

The first version may use BIOS text output. Later output methods must not be assumed available until explicitly initialized.

The loader must avoid endless retries. If a bounded retry policy is later introduced for transient disk errors, the retry count and diagnostic behaviour must be specified and tested.

## 13. Source-code organization

The initial source layout may be:

```text
bootloader/
└── bios/
    ├── stage1/
    │   └── boot.asm
    ├── stage2/
    │   └── stage2.asm
    ├── include/
    └── tools/
        └── image_builder/
```

The exact filenames and build scripts may be refined when the toolchain is selected. Keep boot code, image-generation tools, and generated binary output separate.

Generated files should go into a dedicated build/output directory and should not be confused with source files.

## 14. Build and verification requirements

### 14.1 Static image checks

The build must fail unless:
- Stage 1 is exactly 512 bytes.
- The boot signature is exactly `55 AA` at offsets 510–511.
- Stage 2 fits in the reserved 32-sector region.
- Stage 2 is placed at LBA 1.
- The boot image has the expected sector size and minimum capacity.
- No component overlaps another component's reserved range.
- The image builder's layout report matches the generated image.

### 14.2 VirtualBox boot tests

Use a disposable VM configured for BIOS boot and attach only the generated virtual image. Record the VM configuration used for each test.

Required test cases:
1. Valid image: BIOS loads Stage 1 and Stage 2 displays the expected status.
2. Invalid boot signature: firmware must not be reported as having successfully booted Apokolips OS.
3. Corrupted or missing Stage 2 sectors: Stage 1 must report failure or stop safely.
4. EDD unavailable (simulated in a test harness where practical): Stage 1 must stop with the documented error.
5. Stage 2 entry check: Stage 2 must display its own message only after control reaches its entry point.
6. Rebuild repeatability: rebuilding from the same source and tool versions should produce a functionally identical image; byte-for-byte reproducibility is preferred and differences must be explained.

Later tests must cover manifest corruption, checksum mismatch, invalid ELF headers, out-of-range segments, E820 edge cases, A20 verification, CPU feature absence, and failed long-mode setup.

### 14.3 Test evidence

For every milestone, record:
- Toolchain and VirtualBox versions.
- VM firmware and storage settings.
- Build command and result.
- Image layout report.
- Test steps and observed result.
- Screenshots or logs where useful.
- Known limitations and unresolved defects.

A source file existing or compiling is not proof that the bootloader works.

## 15. Safety rules

- Use only a disposable virtual disk image for bootloader development.
- Do not attach the laptop's Windows system disk to the experimental VM.
- Do not use raw-disk write commands against host physical drives.
- Take a VM snapshot before changing firmware or storage configuration.
- Keep a known-good image for regression testing.
- Verify every image path and target before running a disk-writing command.
- Never run an experimental installer as part of bootloader testing.

| Milestone | Deliverable | Completion evidence |

| BL-0 | Initial toolchain and image-build setup | Hosted NASM/Python versions and reproducible build steps recorded; local VM setup still pending |
| BL-1 | Original Stage 1 and Stage 2 image | 512-byte Stage 1, valid signature, fixed Stage 2 region, image-layout tests pass |

QEMU/SeaBIOS success does not complete the separate Oracle VirtualBox acceptance test. Keep each remaining milestone isolated and require both automated checks and the appropriate runtime evidence.

## 17. Open decisions before coding

The following must be settled and recorded:
1. Exact assembler and version.
2. Exact x86_64 cross-compiler and linker versions for the later kernel stage.
3. Build scripting approach available on the Windows 11 host.
4. VirtualBox version and exact BIOS VM configuration.
5. Whether the initial Stage 2 size cap remains 16 KiB or is revised after a prototype.
6. Exact boot-manifest binary layout and checksum.
7. Exact kernel ELF subset and physical load window.
8. Exact boot-information structure and register ABI.
9. Whether a CHS fallback is ever required.

The initial Stage 1/Stage 2 path and bounded E820 collection have now been implemented and smoke-tested under QEMU/SeaBIOS. Remaining decisions about the manifest format, kernel ELF subset, and hand-off ABI should be resolved in the specific milestones that need them, rather than delaying the existing working boot path.
